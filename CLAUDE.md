What this project is

epiSTEMic is a browser-based platform for authentic computational science investigations targeting grades 6 through undergraduate. The core technical differentiator is Python running entirely in the browser via Pyodide (WebAssembly) — no backend, no login, no external dependencies. The platform is built-to-be-acquired, targeting educational publishers (Macmillan Learning, Cengage, Carolina Biological, HMH, Amplify) over a 5-7 year horizon. Funding path is non-dilutive: NSF STTR, DRK-12, Ben Franklin Technology Partners, KIZ tax credits. Penn State OTM invention disclosure is in progress. I-Corps regional cohort application is underway.

Current stage: this is bootstrapped, pre-funding proof-of-concept work ("vibecoding" with Claude) to produce lessons good enough to get real user/teacher feedback with, not production engineering. The whole codebase is expected to eventually be handed to a hired software engineer once funded, who will build the parts that are explicitly deferred below (accounts, LMS grade passback, any real backend). That handoff is a reason to keep new work as clean, static, and well-documented as the existing units, not a reason to start building backend infrastructure now — infrastructure decisions belong to that future engineer, not to this phase.

Collaborators: Kathy (Penn State, co-inventor, grantsmanship), Duke University biological anthropology researcher (provided primate datasets), Mr. Besong (high school physics teacher, climate investigation notebook).

Working principle throughout this project: The investigation is not a matching game. Mystery specimens are chosen so no single metric resolves the question. Students must synthesize multiple lines of quantitative evidence and make claims with explicitly stated uncertainty. This is intentional and must be preserved in all design decisions.

anthropology/assessment.html — end-of-unit assessment, linked from instructor.html (opens in a new tab, not a download). Generates a randomized transfer specimen client-side on load using a seeded PRNG (mulberry32); the seed lives in the URL so a reload keeps the same specimen but a fresh visit gets a new one. No two students (or sections, or semesters) get the same underlying numbers by default — this is the deliberate fix for the standard problem of assessment answers getting passed down. Randomization is template-based across three archetypes (suspensory_ceboid, cursorial_cercopithecoid, leaping_lemuroid), each with its own genuine multi-metric tension (mirroring the mystery specimens' design), not naive independent-field randomization — that would risk generating a specimen that trivially resolves on one metric or is biologically implausible. Real embedded DATA and CSG_DATA (duplicated from investigation.html, not fetched) form the comparative backdrop in every chart; only the focal specimen's own numbers are generated. Five "data displays" (limb proportion scatter with a species/superfamily view toggle, IMI box plot, body mass table, an interactive click-to-mark OUI number line, CSG box plots with a CA/Imax-Imin toggle) plus ten questions across four parts: reading the displays (with an evidence-selection checklist per question — deliberately not every display is useful for every question), comparing to the student's own earlier mystery specimen, a full claim/evidence/conflicting-evidence/adaptation argument, and a reflection. Submission generates a printable summary (student responses + the exact specimen data they worked from) and a gated "reveal instructor grading reference" section that is auto-computed from that student's specific random values using the same classification logic as the rest of the platform (IMI category ranges, OUI_GROUPS from Drapeau 2004, the CSG interpretation heuristics), not written by hand per student. No backend or login; degrades gracefully if the Plotly CDN fails (each chart's render is independently wrapped, so one failure doesn't take down the body mass table, the OUI canvas, or the rest of the form). Operational note for instructors: the anti-sharing property only holds if students each open the assessment fresh — sharing the literal URL with a ?seed= already in it hands over the same specimen, so distribute the bare assessment.html link, not a URL a previous student generated.

logo.png at the repo root is the shared platform logo, referenced by both index.html and anthropology/instructor.html (via a relative ../logo.png path). Keep it at root rather than duplicating it per unit as more units are added.

The five investigation tabs in detail

Tab 1 (Limb Proportions): Configurable scatter plot and IMI box plot from 478 primate specimens across four superfamilies. Students enter four limb measurements (humerus, radius, femur, tibia), IMI calculates live, mystery specimen plots as a star. Grouping by superfamily/common name/genus. Axes fully configurable. For MS1 only, a "View & Measure (MorphoSource)" panel sits above the measurement form with a bone-switcher (humerus/radius/femur/tibia) driving a real MorphoSource 3D mesh viewer iframe, so the student measures the actual bone model with the viewer's own ruler tool instead of just typing in given numbers — see the MS1 paragraph below.

Tab 2 (Body Mass): Femoral head SI diameter input, five taxon-specific regression equations output simultaneously. Equations: Lemurs exp(2.548×ln(FHSI)+1.696)÷1000, South American Monkeys exp(2.729×ln(FHSI)+1.420)÷1000, Old World Monkeys exp(2.388×ln(FHSI)−4.560), Apes 10^(2.6465×log₁₀(FHSI)−2.4093), Humans 10^(1.7125×log₁₀(FHSI)−1.048). Contextual note auto-generates based on whether human estimate is biologically plausible. For MS1 only, the femur MorphoSource viewer reappears here so the student measures femoral head diameter on the same real mesh rather than the length measured in Tab 1.

Tab 3 (Olecranon Index): OL and UL inputs, OUI calculates live, plots as triangle on a canvas number line against six locomotor group ranges from Drapeau (2004). Groups staggered at three heights to prevent label overlap. Note explicitly states mid-range overlap means OUI alone cannot resolve classification. For MS1 only, a MorphoSource ulna viewer sits above the OL/UL inputs.

Tab 4 (Bone Geometry): ImageJ link bar at top. Drag-and-drop upload for femur and humerus log files (tab-separated ImageJ MomentMacro output: Name, CA, Imax, Imin, Imax/Imin, J). Three switchable charts: log-scale J scatter with 1:1 reference line, Imax/Imin box plots, log-scale cortical area box plots. Femur/humerus/both toggle on box plots. For MS1 only, a "Measure Directly (no ImageJ)" panel sits above the ImageJ upload path — see the MS1 paragraph below for what it does and why its numbers are explicitly estimated, not calibrated.

Tab 5 (Build Argument): Four structured prompts (claim, supporting evidence, conflicting evidence, adaptation/natural selection). Summary pills show all measurements student collected across tabs. Submission calls FEEDBACK_ENDPOINT (a Cloudflare Worker, see cloudflare-worker/worker.js) which holds the Gemini API key server-side and forwards to gemini-3.5-flash. Generates 240-290 word formative feedback that reads all four analyses, does not reveal identity, pushes back on single-metric arguments. The "Reveal identity" button and Identity Revealed panel live here (moved off Tab 1's sidebar so the unlock sits next to the action that earns it) and only arm after the student's second, revised argument submission gets feedback — the first submission's feedback alone does not unlock it, tracked via an in-page submission counter (argumentSubmitCount). A separate, smaller "assessment nudge" card also sits on this tab, always visible so it's discoverable even mid-demo: it starts in a greyed, locked state and flips to a live link to assessment.html once the first submission's feedback comes back, gated on the same epistemic_argument_feedback_received localStorage flag that unlocks the assessment section on student-landing.html. This was deliberately kept as a same-tab link rather than folded into investigation.html as a structural 6th tab, since the assessment generates an unrelated randomized specimen and is meant to be instructor-timed, not an automatic next step in the tab sequence.

The five mystery specimens

MS-11: Alouatta seniculus (Red Howler Monkey), Rio Verde Forest Reserve Colombia. IMI in arboreal quadruped range. Body mass 5-10kg distinguishes from larger species with similar IMI.

MS-12: Presbytis obscura (Dusky Leaf Monkey), Bukit Hijau National Park Malaysia. IMI ~90-91 in dense cercopithecoid overlap zone. Multiple locomotor strategies produce similar values.

MS-13: Indri indri, West African forest (deliberate misdirection — Indri is Malagasy). IMI ~66.5 clusters near humans and sifaka for entirely different evolutionary reasons. Two misdirections: field context wrong, IMI human-like but animal is a vertical clinger and leaper.

MS-14: Erythrocebus patas (Patas Monkey), Kiboko Savanna Sub-Saharan Africa. IMI overlaps with arboreal cercopithecoids despite highly terrestrial cursorial lifestyle. Fastest primate on ground ~55km/h. Habitat context is essential.

MS-1: Papio sp. (Baboon), Kalambo Escarpment, East African Rift Valley. IMI in the low-to-mid 90s sits squarely in arboreal quadruped range despite baboons being among the most terrestrial monkeys — habitat context alone can't resolve it; cross-sectional bone robustness is the deciding evidence. Unlike MS11-14, MS1 uses real specimen tooling rather than given numbers or an uploaded file: Tabs 1-3 embed real MorphoSource 3D mesh viewers (iframes onto morphosource.org manifests) the student measures directly with the viewer's own ruler tool, and Tab 4 adds a "Measure Directly (no ImageJ)" panel — an in-browser Otsu-threshold + pixel-moment CSG tool (canvas-based, algebraically the same math as the ImageJ MomentMacro) running on MS1's own real femur/humerus cross-section images (anthropology/sample-data/MS1_*_midshaft.png), as an alternative to the ImageJ-upload path the other four specimens use. That tool's px/mm scale (femur 9.08, humerus 10.89) is explicitly estimated — back-calculated from the image's own pixel dimensions against published baboon diameter ranges, not a lab calibration — which is an accepted tradeoff specifically because MS1 is a known teaching specimen the platform already runs full analyses on elsewhere, not a novel-research measurement; good for relative bone-robustness comparisons and supporting a claim, not for precise absolute values. Ported from anthropology/prototypes/investigation-ms1-preview.html into the live tool as a 5th specimen; all MS1-specific markup and JS is guarded on specimenKey==="MS1" and hidden by default so MS11-14 are unaffected, and the default specimen (MS13, via the ?specimen= URL param) is unchanged.

Meteorology / Energy Balance unit (sandbox live and linked from the splash page; everything around it still a prototype)

Adapts a Colab notebook a high school physics teacher (Mr. Besong) has used for years — NASA CERES satellite energy-balance data, originally requiring an 800MB NetCDF file plus Cartopy/matplotlib for mapping, both incompatible with Pyodide — into a browser-only tool matching the platform's no-backend/no-external-dependency design. Lives under meteorology/ (promoted from meteorology/prototypes/ to match anthropology/'s flat top-level convention) and is linked from index.html's meteorology tile, badged "Prototype" rather than "Live" since it's only the bare sandbox tool — no narrative landing page, no instructor page, no guided investigations wrapping it yet, unlike anthropology's card.

meteorology/energy-balance-sandbox.html — single-file research sandbox. Students pick a display type (time series, scatter/correlation, spatial trend map, or a non-trend spatial map — see below), a variable, a year range, a month selection (All/Winter DJF/Summer JJA quick-picks or custom), and a lat/lon region (Global/Arctic/Antarctic/Tropics/Hemisphere presets or a custom box), run the analysis, and log a "what do you see / what does it mean / what questions does it raise" notebook entry (localStorage key epistemic_energy_balance_notebook). A "Get AI Feedback" button now reviews that entry — see the dedicated paragraph below for how it differs from the anthropology unit's Tab 5 feedback and why. Trend maps and Maps also have a "Color scale" dropdown (per teacher feedback, students were being pointed at matplotlib's colormap reference page and wanted the same freedom here) — "Auto" keeps the physically-motivated default (diverging, zero-centered for trends and signed variables; sequential, zero-to-max for physically non-negative variables), or a student can force any specific palette, including a diverging one onto a non-negative variable or vice versa, which is left in deliberately since seeing a badly-matched colormap waste half its range is itself the lesson matplotlib's own docs make about choosing colormaps appropriately. Three palettes (Viridis, Cividis, Purple-Orange) are labeled "colorblind-safe" for deuteranopia/protanopia specifically — the rest are left unlabeled rather than guessed at, after an initial version of this feature shipped that label on Pink-Yellow-Green in error (pink carries enough red to sit near the exact red-green confusion axis those conditions involve), caught before merge by direct user feedback.

An "Analysis mode" selector (Explore / Compare) sits above the display panels, added per direct teacher feedback that comparative research — one variable across different seasons, or two variables over the same time/place — is a typical way this kind of investigation actually gets done. Explore is the original single-panel behavior, unchanged. Compare renders a second, fully independent "Build a Display" + "Display" panel pair (its own display type, variable(s), years, months, region, projection, colormap) side by side with the first, both generated from one HTML template function (`buildAnalysisPanelHTML`) keyed by an id suffix ("" for column A, "B" for column B) so the two can never drift apart in markup. Every function that touches these panels' DOM elements takes that same suffix, defaulting to "" so single-column call sites are unaffected. The shared "What Do You See" reflect panel below both columns adapts automatically: if only one column has been run, it behaves exactly as before; if both have, "Log This Entry" and "Get AI Feedback" combine both runs' computed results, and the AI feedback prompt is told explicitly to check the student's description of the *difference* between the two, not just each one in isolation — same grounding-in-computed-numbers approach as the single-run case, just extended to two.

Each display panel also has a "Save PNG" button. For the Plotly-based displays (time series, scatter) this is just `Plotly.downloadImage`, since Plotly already bakes axes/legend/title into the rendered figure. For the canvas-based maps (trend map, map), the legend and title are separate DOM elements, not part of the canvas pixels — exporting the bare canvas would hand a student an unlabeled color map, useless for "save it for a later presentation," so it composites title + map + a redrawn legend gradient (from the same color stops used on screen) onto one offscreen canvas before triggering the download.

The "Map" display type (as opposed to "Trend map") shows a plain spatial snapshot — each cell's average over the selected years/months, not its rate of change — sharing the same fine/coarse tile pipeline and raster renderer (`computeSpatialGrid`'s `mode` argument is "trend" vs. "mean"; `drawSpatialMapCanvas` takes a `colorFn` so it doesn't need to know which). Color scale depends on the variable's `zeroAnchor` flag: physically non-negative variables (ISR, RSR, OLR, cloud fraction, clear-sky OLR, ASR) get a sequential scale from 0 to the region's max, since centering the diverging trend-map scale on 0 would waste half the palette on values that never occur; net flux and cloud radiative effect (legitimately signed — a region can be a net energy source or sink) keep the diverging scale even in Map mode. Unlike a trend map, Map mode works with a single selected year.

Six CERES raw variables (isr, rsr, olr, net, cld, clrolr — incoming solar, reflected shortwave, outgoing longwave, net flux, cloud fraction, clear-sky OLR) plus two derived (asr = isr−rsr, cre = olr−clrolr), matching real CERES EBAF-TOA product variables (solar_mon, toa_sw_all_mon, toa_lw_all_mon, toa_net_all_mon, cldarea_total_daynight_mon, toa_lw_clr_c_mon). Plus four ERA5 reanalysis variables (t2m, sst, siconc, tp — 2m air temperature, sea surface temperature, sea ice cover, precipitation) — see the dedicated "Second dataset" paragraph below for why these were added and what they needed that CERES didn't.

Two-tier resolution architecture: one always-loaded coarse dataset (2°, 90×180 grid, full globe, every month) for time series/scatter work and for scanning the whole globe on a trend map; separate fine-resolution (1°, native CERES resolution) tiles (30°×30° each, 72 tiles cover the globe) fetched only for whichever tiles a selected region overlaps, capped at 12 tiles (~17MB) before automatically falling back to the coarse dataset. This exists because a single global dataset at 1° was empirically ruled out (≈183MB, too large to load on every visit) and because trend maps at 2° were confirmed too coarse to read (a 30°×40° custom region is 300 cells at 2° vs 1200 at 1°).

Trend maps render via hand-rolled spherical projection math (equirectangular, orthographic, stereographic — Snyder's standard forward/inverse formulas), not Plotly's geo traces or Cartopy: Cartopy doesn't work in Pyodide (see above), and a scattergeo-marker approach was tried first and abandoned — no fixed marker size can correctly tile a lat/lon grid under a curved, non-cylindrical projection (confirmed by a visibly broken "pinwheel" render under stereographic at global extent). The working approach inverse-projects every output canvas pixel back to a lat/lon and looks up its cell, which is correct by construction for any projection. A bundled ~76KB world coastline file (110m resolution, decoded offline from the world-atlas npm package via topojson-client, not fetched live) draws over the raster for geographic orientation, clipped to the same region bounds as the data itself — an earlier version clipped coastlines only to the projection's own visibility, not the selected region, so coastlines from well outside the analyzed area could render past the edge of the data.

Data: real CERES EBAF-TOA Edition 4.2.1, monthly, 2001-2025 (25 full years — the record starts March 2000 and the available subset ends April 2026, so both partial-coverage years were dropped). Quantized to int16 with a single global scale factor, gzip-compressed. Getting this data in is worth remembering for next time: this sandbox has no route to fetch anything from NASA Earthdata or Google Drive, so the conversion has to run in a Python environment that already has the file (Colab, in this case), sending back only the small processed output — and even that small output had real trouble getting from a local computer into GitHub. The ~39.5MB coarse file was too large for GitHub's web upload flow; a subsequent attempt got mangled into garbled text after the .gz extension triggered the OS's own archive handler to silently decompress it, and the resulting garbage got pasted through GitHub's "create new file" text editor instead of uploaded as binary. What finally worked: strip the .gz extension entirely before the file leaves Colab (a plain unlabeled binary blob nothing tries to "helpfully" touch), then push via GitHub Desktop rather than the website upload widget, which also silently drops files into the wrong folder when uploaded in separate batches. Verified end to end afterward: decompressed byte counts match the manifest exactly, and the tool's own area-weighted global mean for incoming solar radiation comes out to 340.5 W/m², matching the well-known published value.

Second dataset: ERA5 reanalysis (2m Air Temperature, Sea Surface Temperature, Sea Ice Cover, Precipitation — t2m/sst/siconc/tp), added per teacher feedback that Max's own lesson uses these alongside CERES. Same manifest+gzip pattern, same Colab-conversion pipeline, and — deliberately — regridded during conversion onto CERES's exact lat/lon grid and trimmed to the exact same 2001-2025 year range (ERA5's own record actually starts a full year earlier, at full-year 2000, but CERES's usable range doesn't, and matching CERES rather than ERA5's fuller range is what lets the two datasets share one year index for cross-dataset comparison). This pairing is a deliberate pedagogical complement, not just "more variables": CERES is the energy budget itself (radiation in/out at the top of atmosphere); ERA5's four variables are the observable surface-level consequences of that budget (does the radiation imbalance actually show up in temperature/ice/SST/precipitation trends). The Scatter display type can mix one variable from each dataset directly (e.g. Net Flux vs. 2m Air Temperature) since both share the same grid and year index.

Two things ERA5 needed that CERES didn't: (1) ERA5's four variables span wildly different magnitudes (°C, %, mm/day) so each carries its own quantization scale factor in its manifest, unlike CERES's one shared scale — computeSpatialGrid/regionalMonthlyMeans read a variable's own GRID entry either way, so this needed no shared-format migration, just per-variable scale support in the ERA5 load path. (2) sst and siconc are only defined over ocean (confirmed: ~26.9% of the global grid is missing, matching Earth's land fraction) — a reserved int16 sentinel (-32768) marks missing cells, and every grid-reading function (computeSpatialGrid, regionalMonthlyMeans) skips them rather than averaging in garbage; verified visually (a global SST map correctly renders land as blank, not a corrupted color) and numerically (global mean 2m temperature comes out to 14.57°C, matching the well-known published value, the same kind of sanity check used for CERES's 340.5 W/m²). ERA5 has no fine-resolution regional tiles (unlike CERES's 1° tile system) — the trend-map/map fetch logic checks each variable's `dataset` tag and always uses ERA5's coarse 2° grid regardless of region size, rather than attempting a fine-tile fetch that would 404. One known data quirk worth not mistaking for a bug: ERA5's SST field dips slightly below the real seawater freezing point (~-1.8°C) under sea ice, since ERA5 uses a diagnostic proxy value there rather than a real measurement — this is inherent to the source data and would show up identically in any tool reading the same ERA5 file, including Max's own Colab script.

Important distinction: the Colab notebook referenced above (Mr. Besong's original lesson, used as the source for the sandbox's data/analysis logic) predates public generative AI availability and contains no AI/API calls of any kind — there is no exposed key in it and nothing to route through the Cloudflare Worker. This was previously misdocumented in this file; if AI feedback ever gets asked about for the meteorology unit, it means a new feature to design, not a fix to something already in that notebook.

Terminology note: when this unit's design talks about a "notebook," across every mention in this file it means a pedagogical science notebook — a student-facing log of what was studied, why, what was found, and what it led to (claim/evidence/reasoning), the same spirit as Tab 5's argument-building in the anthropology unit. It does not mean a Jupyter-style code notebook, and Pyodide is not involved in it.

AI feedback: a "Get AI Feedback" button next to "Log This Entry" sends the student's three notebook responses to the same deployed Cloudflare Worker the anthropology unit uses (cloudflare-worker/worker.js — no worker changes were needed, since it's already fully generic: it just proxies {systemPrompt, userPrompt} to Gemini and holds the key server-side, with no idea which unit is calling it). The prompt design is deliberately different from anthropology's Tab 5, because the underlying problem is different: Tab 5 checks an argument against one of four known mystery specimens with a fixed answer key, so it can safely hand the model the correct identity and grade against it. Here, a student can run any variable/region/period combination, so there is no fixed answer key — instead, the prompt hands the model the run's own computed result (the same summary string already shown in the annotation, e.g. "Trend 0.0071 W/m²/yr, r=0.431, mean 340.50 W/m² (...)") as the ONLY ground truth, explicitly forbids inventing additional numbers/facts, and scopes the model to three things: whether the student's "what do you see" matches what was actually computed, whether their "what does it mean" is a plausible mechanism without overreaching what one run can establish, and pushing them toward a concrete next analysis rather than accepting a single metric as sufficient (the same "not a matching game" principle stated at the top of this file, applied here instead of to primate specimens). Verified end-to-end against a mocked worker response (request payload, loading/error states, button text) since this sandbox's own dev environment cannot reach the deployed worker over the network — the actual Gemini output quality has not yet been reviewed by a human and should be checked in a real browser before relying on it.
