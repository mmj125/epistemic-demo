What this project is

epiSTEMic is a browser-based platform for authentic computational science investigations targeting grades 6 through undergraduate. The core technical differentiator is Python running entirely in the browser via Pyodide (WebAssembly) — no backend, no login, no external dependencies. The platform is built-to-be-acquired, targeting educational publishers (Macmillan Learning, Cengage, Carolina Biological, HMH, Amplify) over a 5-7 year horizon. Funding path is non-dilutive: NSF STTR, DRK-12, Ben Franklin Technology Partners, KIZ tax credits. Penn State OTM invention disclosure is in progress. I-Corps regional cohort application is underway.

Current stage: this is bootstrapped, pre-funding proof-of-concept work ("vibecoding" with Claude) to produce lessons good enough to get real user/teacher feedback with, not production engineering. The whole codebase is expected to eventually be handed to a hired software engineer once funded, who will build the parts that are explicitly deferred below (accounts, LMS grade passback, any real backend). That handoff is a reason to keep new work as clean, static, and well-documented as the existing units, not a reason to start building backend infrastructure now — infrastructure decisions belong to that future engineer, not to this phase.

Collaborators: Kathy (Penn State, co-inventor, grantsmanship), Duke University biological anthropology researcher (provided primate datasets), Mr. Besong (high school physics teacher, climate investigation notebook).

Data licensing (confirmed with Duke, 2026-08-28): the MorphoSource specimen data used for MS1 (and the limb-length/CSG datasets more broadly) comes through Despina, Duke's deidentified-data platform, and is open source — no license is needed to use it in this platform. Not an open diligence item; don't re-raise it as a risk unless something changes.

Working principle throughout this project: The investigation is not a matching game. Mystery specimens are chosen so no single metric resolves the question. Students must synthesize multiple lines of quantitative evidence and make claims with explicitly stated uncertainty. This is intentional and must be preserved in all design decisions.

The five investigation tabs in detail

Tab 1 (Limb Proportions): Configurable scatter plot and IMI box plot from 478 primate specimens across four superfamilies. Students enter four limb measurements (humerus, radius, femur, tibia), IMI calculates live, mystery specimen plots as a star. Grouping by superfamily/common name/genus. Axes fully configurable. For MS1 only, a "View & Measure (MorphoSource)" panel sits above the measurement form with a bone-switcher (humerus/radius/femur/tibia) driving a real MorphoSource 3D mesh viewer iframe, so the student measures the actual bone model with the viewer's own ruler tool instead of just typing in given numbers — see the MS1 paragraph below.

Tab 2 (Body Mass): Femoral head SI diameter input, five taxon-specific regression equations output simultaneously. Equations: Lemurs exp(2.548×ln(FHSI)+1.696)÷1000, South American Monkeys exp(2.729×ln(FHSI)+1.420)÷1000, Old World Monkeys exp(2.388×ln(FHSI)−4.560), Apes 10^(2.6465×log₁₀(FHSI)−2.4093), Humans 10^(1.7125×log₁₀(FHSI)−1.048). Contextual note auto-generates based on whether human estimate is biologically plausible. For MS1 only, the femur MorphoSource viewer reappears here so the student measures femoral head diameter on the same real mesh rather than the length measured in Tab 1.

Tab 3 (Olecranon Index): OL and UL inputs, OUI calculates live, plots as triangle on a canvas number line against six locomotor group ranges from Drapeau (2004). Groups staggered at three heights to prevent label overlap. Note explicitly states mid-range overlap means OUI alone cannot resolve classification. Tab 4 (Bone Geometry): ImageJ link bar at top. Drag-and-drop upload for femur and humerus log files (tab-separated ImageJ MomentMacro output: Name, CA, Imax, Imin, Imax/Imin, J). Tab 5 (Build Argument): Four structured prompts (claim, supporting evidence, conflicting evidence, adaptation/natural selection). Summary pills show all measurements student collected across tabs. The five mystery specimens

MS-11: Alouatta seniculus (Red Howler Monkey), Rio Verde Forest Reserve Colombia. IMI in arboreal quadruped range. Body mass 5-10kg distinguishes from larger species with similar IMI.

MS-12: Presbytis obscura (Dusky Leaf Monkey), Bukit Hijau National Park Malaysia. IMI ~90-91 in dense cercopithecoid overlap zone. Multiple locomotor strategies produce similar values.

MS-13: Indri indri, West African forest (deliberate misdirection — Indri is Malagasy). IMI ~66.5 clusters near humans and sifaka for entirely different evolutionary reasons. Two misdirections: field context wrong, IMI human-like but animal is a vertical clinger and leaper.

MS-14: Erythrocebus patas (Patas Monkey), Kiboko Savanna Sub-Saharan Africa. IMI overlaps with arboreal cercopithecoids despite highly terrestrial cursorial lifestyle. Fastest primate on ground ~55km/h. Habitat context is essential.

MS-1: Papio sp. (Baboon), Kalambo Escarpment, East African Rift Valley. IMI in the low-to-mid 90s sits squarely in arboreal quadruped range despite baboons being among the most terrestrial monkeys — habitat context alone can't resolve it; cross-sectional bone robustness is the deciding evidence. Unlike MS11-14, MS1 uses real specimen tooling rather than given numbers or an uploaded file: Tabs 1-3 embed real MorphoSource 3D mesh viewers (iframes onto morphosource.org manifests) the student measures directly with the viewer's own ruler tool, and Tab 4 adds a "Measure Directly (no ImageJ)" panel — an in-browser Otsu-threshold + pixel-moment CSG tool (canvas-based, algebraically the same math as the ImageJ MomentMacro) running on MS1's own real femur/humerus cross-section images (anthropology/sample-data/MS1_*_midshaft.png), as an alternative to the ImageJ-upload path the other four specimens use. That tool's px/mm scale (femur 9.08, humerus 10.89) is explicitly estimated — back-calculated from the image's own pixel dimensions against published baboon diameter ranges, not a lab calibration — which is an accepted tradeoff specifically because MS1 is a known teaching specimen the platform already runs full analyses on elsewhere, not a novel-research measurement; good for relative bone-robustness comparisons and supporting a claim, not for precise absolute values. Ported from anthropology/prototypes/investigation-ms1-preview.html into the live tool as a 5th specimen; all MS1-specific markup and JS is guarded on specimenKey==="MS1" and hidden by default so MS11-14 are unaffected, and the default specimen (MS13, via the ?specimen= URL param) is unchanged.

Engineering unit (structural/civil — cantilever truss design, ground structure method) — very early, in progress

Source materials: Matt provided `Ground_Structure_3x6.mat` (a real MASTAN2 model file) and `Decision_Criteria_Cantilever_FINAL.xlsx` (his existing multi-criteria decision tool), both copied as-is into `engineering/prototypes/` for reference. This unit adapts a real classroom activity (most often taught middle-school tech ed, also used undergrad non-majors): students physically build cantilever trusses out of K'NEX, using MASTAN2 (a Windows desktop matrix-structural-analysis tool, cannot run in-browser) to predict deflection before building. Goal: minimize a weighted combination of deflection, cost, and mass under a fixed tip load — the "ground structure" method, where the full candidate member set is a fixed 28-node grid with 81 possible members, and the design problem is choosing which subset to keep.

The .mat file's model, decoded (do not re-derive this, it's already reverse-engineered and verified): 28 nodes, 7 columns × 4 rows, 4.1875in grid spacing. All 4 left-edge nodes (0-based indices 0, 6, 12, 18) are pinned supports — easy to miss, cost real debugging time (first pass only found 2 of the 4 and got wrong answers). Load is -1.5 lbf downward at node index 24 (bottom-right corner, 1-based node 25) — this is Matt's classroom-scale number, does NOT cleanly convert from "2kg" (2kg×g≈4.4lbf, not 1.5) so treat 1.5lbf as the real load, not a metric conversion. Material is K'NEX plastic: E=30800 psi, A=0.01284 in². All 81 candidate members (elem_info's first 2 columns, 1-based node pairs) are simultaneously present/active in this saved file — it's the full ground structure baseline, not a student's chosen subset.

Decisions locked in with Matt for this build (don't re-ask):
- Preserve the legacy numbers above exactly (not rebuilt with clean SI values) — keeps the browser tool cross-checkable against Matt's real MASTAN2/physical results.
- Auto-derive the bill of materials (rod colors/counts) from the truss topology a student selects, rather than requiring manual entry like the Excel tool. Important correction: the Excel's rod catalog (Black 1.5in ... Orange 20in) is for standard K'NEX and does NOT apply — the real activity uses mini K'NEX (purple 94mm, blue 138mm, both 3mm thick, per Matt directly). See the "Rod-length mapping" paragraph below for the resolved purple/blue assignment.
- Connector (hub) auto-derivation: the Excel's connector formula was written for standard K'NEX and doesn't apply — resolved with real mini K'NEX numbers from Matt directly, see "Connector mass and cost" below.
- Paired with a real physical K'NEX build (not a standalone virtual-only unit like the other two) — the browser tool is pre-build prediction; Tab 4 (planned) is where predicted vs. measured deflection get compared after building.
- No narrative/mystery framing needed (unlike anthropology/meteorology) — present the design brief directly, since the optimization tradeoff itself carries the investigation. Keep language accessible to middle-school-tech-ed level while still working for undergrad non-majors.

The real physical build is 3D, not 2D (clarified 2026-09-02, changes the tab plan below): the actual K'NEX structure is two mirrored copies of this exact 2D ground-structure shape, connected front-to-back with fixed purple/blue cross-bracing. The -1.5lbf modeled load is deliberately half the real hanging mass, since the two mirrored faces share it — this was already correctly baked into the legacy MASTAN numbers, it just wasn't explained anywhere in the UI (now fixed, see below). Decided NOT to make the interactive tool 3D: splitting a symmetric space truss into a planar sub-analysis at half-load is a standard, legitimate real engineering simplification, not a compromise — and a real 3D tool (WebGL/Three.js, camera controls, 3D hit-testing) is a large build for an audience (8th grade, see below) that can't use trig to interpret 3D force resolution anyway. This only holds as long as the cross-bracing between the two faces stays fixed/given rather than becoming its own student design choice — if that ever changes, revisit. `truss-designer.html`'s header now states this explicitly: it's one face of the real build, the load is half the real mass because both faces share it, and any member removed on screen should be removed from both physical faces (the cross-bracing stays as built).

Audience constraint (clarified 2026-09-02): this is currently taught in 8th grade (also works for undergrad non-majors, per earlier notes) — students can't do the method of joints, since it needs trigonometry they don't have yet. The software was always going to hide that math (same as MASTAN2 did), so this doesn't block the design-tool itself. What it does change is the scaffolding before it: without method-of-joints, students need a different, non-trig path to the qualitative structural intuition (why is this member stretching vs squishing, why does this shape hold its form, where does the load actually go) that lets them read the Element Report and make informed choices rather than clicking randomly. Matt confirmed the existing MASTAN-based version of this activity already works well for this audience (students reliably end up with non-collapsing designs) — the scaffolding redesign below is about making the reasoning more genuine and the tool more polished within that already-working format, not fixing something broken.

meteorology/energy-balance-sandbox.html — single-file research sandbox. Students pick a display type (time series, scatter/correlation, spatial trend map, or a non-trend spatial map — see below), a variable, a year range, a month selection (All/Winter DJF/Summer JJA quick-picks or custom), and a lat/lon region (Global/Arctic/Antarctic/Tropics/Hemisphere presets or a custom box), run the analysis, and log a "what do you see / what does it mean / what questions does it raise" notebook entry (localStorage key epistemic_energy_balance_notebook). Trend maps and Maps also have a "Color scale" dropdown (per teacher feedback, students were being pointed at matplotlib's colormap reference page and wanted the same freedom here) — "Auto" keeps the physically-motivated default (diverging, zero-centered for trends and signed variables; sequential, zero-to-max for physically non-negative variables), or a student can force any specific palette, including a diverging one onto a non-negative variable or vice versa, which is left in deliberately since seeing a badly-matched colormap waste half its range is itself the lesson matplotlib's own docs make about choosing colormaps appropriately. An "Analysis mode" selector (Explore / Compare) sits above the display panels, added per direct teacher feedback that comparative research — one variable across different seasons, or two variables over the same time/place — is a typical way this kind of investigation actually gets done. Explore is the original single-panel behavior, unchanged. Compare renders a second, fully independent "Build a Display" + "Display" panel pair (its own display type, variable(s), years, months, region, projection, colormap) side by side with the first, both generated from one HTML template function (`buildAnalysisPanelHTML`) keyed by an id suffix ("" for column A, "B" for column B) so the two can never drift apart in markup. Every function that touches these panels' DOM elements takes that same suffix, defaulting to "" so single-column call sites are unaffected. The shared "What Do You See" reflect panel below both columns adapts automatically: if only one column has been run, it behaves exactly as before; if both have, "Log This Entry" and "Get AI Feedback" combine both runs' computed results, and the AI feedback prompt is told explicitly to check the student's description of the *difference* between the two, not just each one in isolation — same grounding-in-computed-numbers approach as the single-run case, just extended to two.

Each display panel also has a "Save PNG" button. For the Plotly-based displays (time series, scatter) this is just `Plotly.downloadImage`, since Plotly already bakes axes/legend/title into the rendered figure. For the canvas-based maps (trend map, map), the legend and title are separate DOM elements, not part of the canvas pixels — exporting the bare canvas would hand a student an unlabeled color map, useless for "save it for a later presentation," so it composites title + map + a redrawn legend gradient (from the same color stops used on screen) onto one offscreen canvas before triggering the download.

The "Map" display type (as opposed to "Trend map") shows a plain spatial snapshot — each cell's average over the selected years/months, not its rate of change — sharing the same fine/coarse tile pipeline and raster renderer (`computeSpatialGrid`'s `mode` argument is "trend" vs. "mean"; `drawSpatialMapCanvas` takes a `colorFn` so it doesn't need to know which). Color scale depends on the variable's `zeroAnchor` flag: physically non-negative variables (ISR, RSR, OLR, cloud fraction, clear-sky OLR, ASR) get a sequential scale from 0 to the region's max, since centering the diverging trend-map scale on 0 would waste half the palette on values that never occur; net flux and cloud radiative effect (legitimately signed — a region can be a net energy source or sink) keep the diverging scale even in Map mode. Unlike a trend map, Map mode works with a single selected year.

Six CERES raw variables (isr, rsr, olr, net, cld, clrolr — incoming solar, reflected shortwave, outgoing longwave, net flux, cloud fraction, clear-sky OLR) plus two derived (asr = isr−rsr, cre = olr−clrolr), matching real CERES EBAF-TOA product variables (solar_mon, toa_sw_all_mon, toa_lw_all_mon, toa_net_all_mon, cldarea_total_daynight_mon, toa_lw_clr_c_mon). Plus five ERA5 reanalysis variables (t2m, sst, siconc, tp, strd — 2m air temperature, sea surface temperature, sea ice cover, precipitation, downward longwave/DLR) — see the dedicated "Second dataset" paragraph below for why these were added and what they needed that CERES didn't.

Two-tier resolution architecture: one always-loaded coarse dataset (2°, 90×180 grid, full globe, every month) for time series/scatter work and for scanning the whole globe on a trend map; separate fine-resolution (1°, native CERES resolution) tiles (30°×30° each, 72 tiles cover the globe) fetched only for whichever tiles a selected region overlaps, capped at 12 tiles (~17MB) before automatically falling back to the coarse dataset. This exists because a single global dataset at 1° was empirically ruled out (≈183MB, too large to load on every visit) and because trend maps at 2° were confirmed too coarse to read (a 30°×40° custom region is 300 cells at 2° vs 1200 at 1°).

Trend maps render via hand-rolled spherical projection math (equirectangular, orthographic, stereographic — Snyder's standard forward/inverse formulas), not Plotly's geo traces or Cartopy: Cartopy doesn't work in Pyodide (see above), and a scattergeo-marker approach was tried first and abandoned — no fixed marker size can correctly tile a lat/lon grid under a curved, non-cylindrical projection (confirmed by a visibly broken "pinwheel" render under stereographic at global extent). The working approach inverse-projects every output canvas pixel back to a lat/lon and looks up its cell, which is correct by construction for any projection. A bundled ~76KB world coastline file (110m resolution, decoded offline from the world-atlas npm package via topojson-client, not fetched live) draws over the raster for geographic orientation, clipped to the same region bounds as the data itself — an earlier version clipped coastlines only to the projection's own visibility, not the selected region, so coastlines from well outside the analyzed area could render past the edge of the data.

Data: real CERES EBAF-TOA Edition 4.2.1, monthly, 2001-2025 (25 full years — the record starts March 2000 and the available subset ends April 2026, so both partial-coverage years were dropped). Quantized to int16 with a single global scale factor, gzip-compressed. Getting this data in is worth remembering for next time: this sandbox has no route to fetch anything from NASA Earthdata or Google Drive, so the conversion has to run in a Python environment that already has the file (Colab, in this case), sending back only the small processed output — and even that small output had real trouble getting from a local computer into GitHub. The ~39.5MB coarse file was too large for GitHub's web upload flow; a subsequent attempt got mangled into garbled text after the .gz extension triggered the OS's own archive handler to silently decompress it, and the resulting garbage got pasted through GitHub's "create new file" text editor instead of uploaded as binary. What finally worked: strip the .gz extension entirely before the file leaves Colab (a plain unlabeled binary blob nothing tries to "helpfully" touch), then push via GitHub Desktop rather than the website upload widget, which also silently drops files into the wrong folder when uploaded in separate batches. Verified end to end afterward: decompressed byte counts match the manifest exactly, and the tool's own area-weighted global mean for incoming solar radiation comes out to 340.5 W/m², matching the well-known published value.

Second dataset: ERA5 reanalysis (2m Air Temperature, Sea Surface Temperature, Sea Ice Cover, Precipitation — t2m/sst/siconc/tp), added per teacher feedback that Max's own lesson uses these alongside CERES. Same manifest+gzip pattern, same Colab-conversion pipeline, and — deliberately — regridded during conversion onto CERES's exact lat/lon grid and trimmed to the exact same 2001-2025 year range (ERA5's own record actually starts a full year earlier, at full-year 2000, but CERES's usable range doesn't, and matching CERES rather than ERA5's fuller range is what lets the two datasets share one year index for cross-dataset comparison). This pairing is a deliberate pedagogical complement, not just "more variables": CERES is the energy budget itself (radiation in/out at the top of atmosphere); ERA5's four variables are the observable surface-level consequences of that budget (does the radiation imbalance actually show up in temperature/ice/SST/precipitation trends). The Scatter display type can mix one variable from each dataset directly (e.g. Net Flux vs. 2m Air Temperature) since both share the same grid and year index.

Two things ERA5 needed that CERES didn't: (1) ERA5's four variables span wildly different magnitudes (°C, %, mm/day) so each carries its own quantization scale factor in its manifest, unlike CERES's one shared scale — computeSpatialGrid/regionalMonthlyMeans read a variable's own GRID entry either way, so this needed no shared-format migration, just per-variable scale support in the ERA5 load path. (2) sst and siconc are only defined over ocean (confirmed: ~26.9% of the global grid is missing, matching Earth's land fraction) — a reserved int16 sentinel (-32768) marks missing cells, and every grid-reading function (computeSpatialGrid, regionalMonthlyMeans) skips them rather than averaging in garbage; verified visually (a global SST map correctly renders land as blank, not a corrupted color) and numerically (global mean 2m temperature comes out to 14.57°C, matching the well-known published value, the same kind of sanity check used for CERES's 340.5 W/m²). ERA5 has no fine-resolution regional tiles (unlike CERES's 1° tile system) — the trend-map/map fetch logic checks each variable's `dataset` tag and always uses ERA5's coarse 2° grid regardless of region size, rather than attempting a fine-tile fetch that would 404. One known data quirk worth not mistaking for a bug: ERA5's SST field dips slightly below the real seawater freezing point (~-1.8°C) under sea ice, since ERA5 uses a diagnostic proxy value there rather than a real measurement — this is inherent to the source data and would show up identically in any tool reading the same ERA5 file, including Max's own Colab script.

Agricultural unit (crop/soil modeling, adapting the real CYCLES agroecosystem model) — very early, in progress

Source material: a Colab notebook (`Copy_of_Cycles_CONUS_using_Cycles_utils.ipynb`, committed to `main`) that runs the real CYCLES model (Penn State, Kemanian et al.) for a user-defined field boundary. The notebook downloads gSSURGO soil data, NLDAS-2 weather, and generates Cycles input files via the `cycles-utils` pip package, then executes a compiled Cycles binary and plots results. Matt has a direct working relationship with the CYCLES developers and expects them to be receptive to this use.

Licensing (the central constraint on this whole unit, read before doing anything else here): Cycles is released under **CC BY-NC-ND 4.0** (verified directly from `LICENSE.md` in github.com/PSUmodeling/Cycles) — noncommercial only and no derivatives, both in tension with this platform's eventual commercial-acquisition model and with "modify Cycles for classroom use" specifically. Getting explicit permission from the devs is in progress (Matt reaching out directly) but not yet confirmed in writing — don't treat it as resolved. Separately, the input-data pipeline (gSSURGO/GADM/NLDAS) reads from a private "Cycles global simulation database" Google Shared Drive Matt has access to but this sandbox does not — any static data this unit ships needs Matt to run the Colab preprocessing himself and export the result, same pattern as CERES/ERA5.

Four technical paths for getting the real model working have now been investigated; three are closed off or set aside:
- **WASM compilation of the real source**: not attempted, because there is no public source to compile. The public `PSUmodeling/Cycles` GitHub repo and every other repo in that GitHub org ships only compiled binaries and sample input/output files — confirmed by downloading the actual v1.4.4 release zip and inspecting its contents (one ELF binary, no `.c`/`.h` anywhere), and the repo's own README says outright "this repository is used to release Cycles executables," not source. Emscripten itself installs and works fine in this sandbox — the blocker is purely the missing source, not the toolchain.
- **v86 (run the real unmodified Linux binary inside a browser-based x86 emulator, no source needed)**: built and tested a real headless boot harness (Node.js + the `v86` npm package + a real bootable Linux ISO, `linux4.iso`, committed to `main` at Matt's request after the correct host, `i.copy.sh`, was tracked down from v86's own CI pipeline — an earlier guess at `k.copy.sh` was wrong and got corrected). The real Cycles binary was actually pushed into the emulator's 9p virtual filesystem and executed — and failed with a BusyBox "applet not found" error. Root cause, confirmed directly: `uname -a` inside the booted guest reports a 32-bit i686 kernel, and v86's own Readme states plainly "64-bit kernels are not supported" as an explicit, permanent project limitation, not a missing image to hunt down. Cycles only ships 64-bit Linux builds (checked: no `Cycles_i386` release exists). This path is dead for this specific binary, conclusively, not just difficult — don't re-attempt it without a fundamentally different emulator.
- **Small backend running the real binary server-side**: prototyped and proven to work (`POST /simulate` → real Cycles execution → parsed JSON, tested against two different real rotations with physically distinct results, not a canned response). Deliberately not deployed anywhere — this breaks the platform's stated no-backend architecture (see "Current stage" and "What is deliberately deferred" above), and Matt chose to pursue it only as a fallback/comparison, not the primary path. The prototype code was not committed to this repo (it lived in the sandbox only) since it was explicitly exploratory.
- **Blink (x86-64 emulator) compiled to WebAssembly, running the real unmodified binary client-side**: unlike v86, Blink supports 64-bit guests, so this path actually works — see the dedicated "WASM-Cycles investigation" paragraph below for the full technical account and why it's set aside for the live tool anyway (speed, not correctness).

The path actually being pursued now: a **from-scratch reimplementation**, independently built from Cycles' own published methodology rather than its code — legally clean regardless of the licensing outcome (copyright protects the specific code expression, not the underlying published science; 17 U.S.C. §102(b)), and it doesn't need source, a backend, or an emulator. Matt supplied both the primary methods paper (Kemanian et al. 2024, *Computers and Electronics in Agriculture* 227, "The Cycles Agroecosystem Model: Fundamentals, Testing, and Applications") and its Supplemental Information document, which together give real, complete, numbered governing equations for water/energy balance, canopy growth and yield, curve-number runoff, and soil carbon/nitrogen saturation dynamics — not just descriptions. Two likely-systematic sign errors were found in the SI's typeset equations (the runoff denominator and the wet-curve-number formula both show a `−` where the external standard methods they cite, and basic algebraic derivation, require `+` — implemented with the corrected sign in both cases, flagged in code). Per-crop numeric parameters (radiation/transpiration-use efficiency, phenology thresholds, harvest-index bounds) come from the real `GenericCrops.crop` file bundled with the public binary release itself — genuine input data the software reads at runtime, not literature guesses.

Scope for v1 (decided directly with Matt): all three of Cycles' bundled sample rotations (continuous corn, corn-silage-soy-wheat, corn-soy-wheat-pasture — the last one pulls in winter wheat and cut-and-regrow perennial forage species, real added complexity worth having named). Water balance and yield only — full nitrogen/carbon cycling (the model's own claimed core innovation) is explicitly deferred; real Cycles output confirms zero nitrogen stress in the validated reference scenario anyway, so skipping it isn't costing accuracy there. Nitrogen rate is kept as a student-facing knob via a simplified mineral-N balance (fertilizer applied minus crop uptake minus basic leaching) rather than the full six-pool soil C/N system. Arbitrary KML field upload (the feature that originally motivated this whole investigation) is explicitly out of scope for now, deferred to a later pass once a validated engine exists — not to be silently assumed back into v1.

What's built and validated so far: `agricultural/prototypes/cycles_engine_validate.py`, an independent Python engine (no Cycles code or binary in it, and deliberately no Cycles-generated reference data committed alongside it either — see the file's own docstring for why: republishing Cycles' *output* may need the same permission as the model itself, an open question for the devs that hasn't been asked yet). Validated against real Cycles v1.4.4 output for the Rock Springs, PA continuous-corn sample scenario (37 years, 1980-2016):
- Reference evapotranspiration (FAO-56 Penman-Monteith, a standard external public formula): matches real Cycles' own output to 0.008 mm/day mean absolute error across the full record — essentially exact, as expected of a correctly-implemented standard method.
- Curve-number runoff: right order of magnitude, not a clean match — the model's own moisture-adjustment factor (`fwc`) is described only in words in the SI ("1 for soil saturated to 0.6m depth... depth-weighted toward the surface"), not given as an exact formula; the current implementation is a defensible interpretation, not verified exact.
- Soil-temperature-triggered planting: no soil temperature formula is disclosed in either source (the SI's own process flowchart marks it as covered, but the actual equation isn't there — same gap as soil evaporation, below). A standard lag-filter proxy of air temperature was used instead and validated directly against real per-year planting dates: 2.65 days mean absolute error across all 37 years.
- Crop growth and yield: went from actively backwards (a first, ad hoc proxy model — not the one in this file — had *negative* year-to-year correlation with real output, rating real drought years as the best years) to 0.744 correlation once real soil-moisture stress was coupled into transpiration (the model initially used pure atmospheric-demand-based potential transpiration with no soil-moisture limit at all, so it could never be more water-stressed than the atmosphere alone implied, no matter how dry the actual soil was). After that fix, four candidate explanations for a remaining ~20-25% absolute-level overestimate were tested and none panned out: canopy cover trajectory checked out fine against real daily output; real nitrogen stress is zero in this scenario so isn't the cause; CO2 scaling of radiation-use-efficiency is undisclosed in both sources and implausible to be large for a C4 crop like corn; cold-temperature transpiration stress is a real, disclosed mechanism (now implemented, using real crop-file thresholds) but has negligible effect at this site. Rather than keep guessing, a disclosed calibration factor was applied to bring the absolute mean in line with real output — it does not affect year-to-year correlation, only scale. That factor was later found to be covering for a real, separate bug (see the update further below, from validating the other two rotations) — after fixing it, the correct residual calibration factor is smaller (0.876, not 0.645). Current validated numbers: mean yield 10.97 vs. real 10.93 Mg/ha, mean absolute error 0.52 Mg/ha, correlation 0.759.
- Bare-soil evaporation: no disclosed formula in either source (again, the flowchart marks it as covered; the actual equation isn't there) — implemented as a standard proxy (ETo scaled by non-intercepted radiation fraction, limited by available surface-layer water), not a verified Cycles formula.

Update from validating the other two rotations (in progress): most of the ~20-25% level gap noted above turned out to be a real, fixable bug, not an unidentified missing mechanism. Real Cycles' own `HARVEST_INDEX` column is defined as grain ÷ *aboveground* biomass (verified exactly: 11.61 / (26.17 - 3.48 root) = 0.5117, matching the real reported value; 11.61 / 26.17 does not), but the model had been applying harvest index to *total* biomass the whole time. Fixed by adding real shoot/root partitioning (Eq. SI.8-11, using the crop file's real INITIAL/FINAL_PARTITIONING_TO_SHOOT values; the equation's own TTf50 half-max parameter has no disclosed numeric value in either source, so the literal reading of its name, 0.5, was used, flagged in code). After the fix: grain corn's pre-calibration ratio dropped from 1.55 to 1.14 and correlation improved 0.744 → 0.768; soybean similarly improved (ratio 0.78 → 0.90, correlation 0.83 → 0.85). Calibration factors are now applied per-crop (`crop["calibration_factor"]` in code), not as one global constant, since soybean's residual runs the opposite direction from corn's — confirmed this isn't one uniform missing mechanism.

Winter wheat and silage corn, by contrast, are still rough. Wheat's correlation got *worse* after the AG-biomass fix (0.535 → 0.362) — diagnosed properly rather than guessed at: thermal-time accumulation was checked directly against real Cycles output and ruled out (ours: 1783.6, real: 1740.76 by harvest, within 2.5%), but canopy cover was not: at the point real Cycles shows 0.746 canopy cover, the paper's default shape constants (calibrated for corn, explicitly stated to represent "a normalized plant density of 1" for that case) predict 0.886, a real, verified gap. A wheat-specific refit of those shape constants (fit against 13 real data points from one real season) improved the level bias (yield ratio 1.51 → 1.40, now calibrated to match the mean exactly) but did NOT fix correlation (0.362 → 0.253, still worse than before the AG-biomass fix) — the actual driver of wheat's weak year-to-year tracking remains unidentified after two real diagnostic attempts.

Silage corn got the same treatment and turned up something more general. Every individual mechanism checks out: thermal time matches real Cycles within 1%, canopy cover matches within a few percent at every checked date, harvest date (triggered at `HARVEST_TIMING=85` → 85% of thermal time to maturity, confirmed directly from the crop file and the operation file's own comment explaining why forage crops aren't given a fixed harvest date) matches real dates to 1.1 days mean error across 13 years, and the aboveground-biomass-to-forage-yield ratio is a rock-solid 0.9499-0.9500 across all 13 real harvests. None of that explains correlation stuck at 0.503. A day-by-day residual check (the same technique that found the AG-biomass bug) found the real, if small, cause of the *level* bias: the paper's canopy-cover defaults run about 5% high at peak even for corn itself (real 0.943 vs. predicted 0.990) — negligible for grain corn, since by the time this matters the crop is already senescing and growth has stopped, but silage corn is harvested mid-peak-growth (85% of maturity, not 100%), so the same small daily overestimate compounds for weeks longer before harvest (AG biomass ratio to real output grows from 1.00 at mid-season to 1.25 by harvest). A corn-specific canopy refit (6, -20, -12, 12, also applied to grain corn, nudging its correlation up to 0.771) fixed silage corn's level bias but barely moved its correlation (0.503 → 0.501) — confirming the level bias and the correlation problem are two separate things, and the correlation problem in both wheat and silage corn is still genuinely unresolved. What the two failing-correlation crops share, that corn/soybean don't: neither is harvested at full senescence (silage stops at 85% of maturity while still actively growing; wheat crosses a real winter) — logged as a specific, evidence-backed question rather than continuing to guess.

Follow-up diagnostic session (2026-09-10, correlation numbers unchanged — this was pure diagnosis, no fix landed): went looking for the actual driver behind wheat's and silage corn's stuck correlation by directly comparing this model's day-by-day water stress against real Cycles' own `WATER STRESS` output column (never previously checked directly) — and found two genuinely different problems hiding under one symptom.
- **Silage corn**: stress *magnitude* is right (real layer 1-3 soil moisture during the 2016 peak is genuinely down near wilting point, 0.13-0.17 m3/m3 — a real drought, nothing anomalous), but *timing* is off by about 11 days (model onsets 2016-07-11, real onsets 2016-06-30), and the within-event shape differs. Three independent, principled fixes were swept across all four validated crops to see if any single recalibration closed this without breaking corn/soybean: raising the stress-onset threshold (0.5→0.8), slowing root growth rate, and widening bare-soil evaporation's extraction depth to FAO-56's standard 0.10-0.30m (a real public constant, not a guess). None meaningfully moved silage corn's correlation, and all three modestly hurt corn/soybean as the parameter increased — ruling out simple recalibration and pointing at the soil water *redistribution* physics itself (the paper's real Eq. 1-2 is a sub-daily, capacitance-weighted flow calculation; this engine approximates it with a same-day cascading bucket, flagged as such in the module docstring since the first validation pass). Implementing the real physics needs soil hydraulic parameters (pore-size distribution exponent, air-entry potential, saturated hydraulic conductivity) that Saxton-Rawls (2006) reportedly also provides — but every source tried to verify the exact secondary formulas (four different mirrors) was blocked by this sandbox's network egress policy, not confirmed as paywalled. Added to the dev-questions list as a real, disclosed-but-unverifiable-here item rather than guessing at coefficients.
- **Winter wheat**: a stranger, structurally different anomaly, not a timing problem. Real wheat yield correlates -0.89 with real Cycles' own max-per-season water stress across all 9 harvested years — confirming stress is genuinely the dominant driver, not a red herring. But this model's max-per-season stress only correlates 0.37 against real Cycles', and shows *zero* stress in three years (2003, 2009, 2012) where real Cycles reports 27-60%. Traced the worst case (2012, real peak 59.5% on 2012-03-16) directly against real Cycles' own soil-moisture output for that date: layer-1 moisture is 0.305 m3/m3 against a field capacity of 0.339 — only mildly depleted, ~83% of field capacity — while the crop is still early vegetative growth (thermal time 42% to maturity). No standard depletion-fraction stress function would produce 60% stress from that mild a deficit. First suspected a winter-dormancy desync in the thermal-time engine; ruled out by comparing day-by-day (not just season-total) thermal time against real Cycles' own column across a full season — every checkpoint matches within 1-3%, including both going flat in December-January. So wheat's real water-stress mechanism is doing something this model isn't modeling at all (a shallower/slower real root-growth curve specific to wheat, a much more nonlinear stress response, or an early-season restriction that isn't moisture-driven in the way assumed) — logged as a sharp, evidence-backed question rather than more blind tuning. Full detail on both findings, including the ruled-out fixes so they aren't re-attempted, in `agricultural/prototypes/QUESTIONS_FOR_DEVS.md` items 6-7.

Nitrogen knob (built this session): the fertilizer-rate slider decided earlier in this unit's planning ("nitrogen rate is kept as a student-facing knob via a simplified mineral-N balance... rather than the full six-pool soil C/N system") is now actually wired into `simulate_season()` (both `cycles_engine_validate.py` and the embedded copy in `engine-demo.html`, kept in sync) as an optional `n_rate_kg_ha` parameter -- `None` (the default when not passed) skips it entirely, byte-identical to the pre-nitrogen behavior, verified by re-running `run_validation.py`/`run_validation_rotation2.py` unchanged (corn 0.771, soybean 0.846, wheat 0.253, silage corn 0.501, all exactly as before). Two real, disclosed mechanisms, grounded in each crop's actual `GenericCrops.crop` values (corn: N_MAX_CONCENTRATION=0.055, N_DILUTION_SLOPE=0.4; soybean: 0.07, 0.4), not literature guesses:
- **N demand**: a standard critical-N-dilution-curve model (Justes et al. 1994 / Lemaire dilution theory -- a widely used simplification, not a Cycles invention), flat at N_MAX_CONCENTRATION below 1 Mg/ha biomass, declining as biomass^-dilution_slope above it. Caught a real bug before shipping: naively multiplying that whole-plant *average* concentration by each day's new growth overcounts (it double-counts already-accumulated tissue's N on every day), inflating total seasonal demand to ~668 kg N/ha for a ~30 Mg/ha corn crop -- verified wrong by checking against realistic total-uptake references. Fixed by using the actual *marginal* rate (the derivative of total plant N content with respect to biomass, which carries a `(1 - dilution_slope)` factor), confirmed correct by checking that an unconstrained run (`n_rate_kg_ha` very high) exactly reproduces the no-nitrogen-tracking baseline, and that a rate near the closed-form total demand causes partial, not total, stress.
- **Leaching**: reuses the water balance's own daily drainage output (`redistribute()`'s return value, previously discarded, now captured) in a simple "well-mixed reservoir" model -- nitrate washes out in proportion to how much water leaves the soil profile and how concentrated the remaining N pool is. A disclosed, defensible proxy, not a verified Cycles formula, same spirit as this file's existing soil-evaporation and `fwc` approximations.

Nitrogen response curve fixed, economic tradeoff added (2026-09-14, same day, after Matt tried the live demo): Matt reported the rotation/N-sweep demo showed no diminishing returns at all -- yield just kept climbing until a hard wall at 650 kg N/ha -- and asked why, correctly guessing there should be diminishing returns in growth and an eventual runoff/cost tradeoff. The actual structural fix: a new `_reference_n_demand()` helper deliberately duplicates the main loop's water/canopy physics (not a call to `simulate_season` itself, so it can be read and audited directly) with no nitrogen feedback at all, exploiting the fact that dGB_water_limited never depends on biomass or N status -- canopy cover is a function of thermal-time fraction alone, water-limited growth depends only on soil moisture. This precomputes the day-by-day nitrogen DEMAND of the fully unconstrained trajectory up front, letting `simulate_season()` apply nitrogen adequacy as a single WHOLE-SEASON fraction (total available N supply over total season demand) instead of a day-by-day pool that can hit a hard, uncorrectable zero. The fraction uses a quadratic-plateau shape (`f(x) = 2x - x^2` for `x` = supply/demand capped at 1) rather than a plain linear-plateau -- both are real, standard functional forms in the actual agronomic N-response literature (e.g. Cerrato & Blackmer 1990), but a straight linear-plateau has constant marginal return right up to a sharp corner, which would make the later economic-optimum calculation degenerate into a step function instead of a genuine interior maximum; the quadratic-plateau gives real, smoothly diminishing returns throughout. The day-by-day fertilizer pool is still tracked, but only to give leaching a real trajectory (surplus N left over after the season's rationed uptake washes out with drainage as before) -- it no longer drives growth stress directly. Verified: 2012 and 1993 corn now both show a smooth, genuinely concave yield-vs-N curve (e.g. 2012: marginal yield per 25 kg N/ha declining from +0.999 near N=25 down through +0.015 near N=400, then flat) instead of the old accelerating-then-cliff shape, with leaching still climbing steadily across the whole range as expected.

Root cause: three call sites (the tillage-compare panel's low/high nitrogen comparison, and the nitrogen-balance panel's rain and soil comparisons) fired two `pyodide.runPythonAsync()` calls concurrently via `Promise.all()`, but both calls write their inputs into the *same shared Pyodide global namespace* (`tc_n_rate` etc.) before either one's Python body actually reads it back. Real Pyodide yields to the JS event loop internally (loading imports) before running the code string, so the second call's `globals.set()` fires and overwrites the first call's inputs before the first call's Python ever executes -- both runs silently ended up using whichever rate won the race (in JS's left-to-right evaluation order, almost certainly the second, higher one). At 650 kg N/ha all five tillage implements are already validated to converge to the identical value, which is exactly why every bar looked the same rather than showing the expected staircase at the low rate. Two already-shipped panels (Tab 2's year-compare and soil-compare) do the equivalent comparison correctly, sequentially with `await`, not `Promise.all` -- confirmed as the reason Matt saw this only on tillage, not there. Fixed by serializing all three call sites to sequential `await`s, the same pattern the working panels already used; verified with a mocked-Pyodide test that reproduces Pyodide's real yield-before-execute timing (a `setTimeout` delay inside the mocked `runPythonAsync`, deliberately built to actually expose the race rather than assume it away) and confirms each call now reads back the rate it was actually given, both at call time and at "execution" time. Worth remembering the shape of this bug for any future panel in this project that runs two `pyodide.runPythonAsync()` calls side by side: Pyodide has exactly one global Python namespace, so concurrent calls that both use `pyodide.globals.set()` are unsafe by construction, regardless of how independent the two calls look in JS -- `Promise.all()` is only safe here when every promise in it is pure JS (like `resolveSiteAt()`'s fetch/decode work), never when any of them touch `pyodide.globals`.
