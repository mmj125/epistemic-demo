epiSTEMic Platform — Primate Locomotion Investigation

What this project is

epiSTEMic is a browser-based platform for authentic computational science investigations targeting grades 6 through undergraduate. The core technical differentiator is Python running entirely in the browser via Pyodide (WebAssembly) — no backend, no login, no external dependencies. The platform is built-to-be-acquired, targeting educational publishers (Macmillan Learning, Cengage, Carolina Biological, HMH, Amplify) over a 5-7 year horizon. Funding path is non-dilutive: NSF STTR, DRK-12, Ben Franklin Technology Partners, KIZ tax credits. Penn State OTM invention disclosure is in progress. I-Corps regional cohort application is underway.

Current stage: this is bootstrapped, pre-funding proof-of-concept work ("vibecoding" with Claude) to produce lessons good enough to get real user/teacher feedback with, not production engineering. The whole codebase is expected to eventually be handed to a hired software engineer once funded, who will build the parts that are explicitly deferred below (accounts, LMS grade passback, any real backend). That handoff is a reason to keep new work as clean, static, and well-documented as the existing units, not a reason to start building backend infrastructure now — infrastructure decisions belong to that future engineer, not to this phase.

Collaborators: Kathy (Penn State, co-inventor, grantsmanship), Duke University biological anthropology researcher (provided primate datasets), Mr. Besong (high school physics teacher, climate investigation notebook).

Working principle throughout this project: The investigation is not a matching game. Mystery specimens are chosen so no single metric resolves the question. Students must synthesize multiple lines of quantitative evidence and make claims with explicitly stated uncertainty. This is intentional and must be preserved in all design decisions.

Current build state

The platform is multi-unit now. index.html at the repo root is the epiSTEMic splash page: logo, tagline, and a unit-selection grid. It is the live root at https://mmj125.github.io/epistemic-demo/. It links to two unit tiles — Biological Anthropology (badged "Live," links to anthropology/student-landing.html as the primary action, with a secondary "Instructor resources" link to anthropology/instructor.html) and Meteorology & Climate Science (badged "Prototype," links directly to meteorology/energy-balance-sandbox.html — deliberately not badged "Live" and not framed as a full unit the way anthropology's card is, since there's no narrative landing page, no instructor page, and no guided investigations around it yet, just the sandbox tool itself; the card copy says so explicitly). A non-functional "Sign In" placeholder sits in the top corner; accounts are not built yet.

Each unit's files live in their own top-level folder so additional subjects can be added the same way. The anthropology unit is under anthropology/:

anthropology/instructor.html — teacher-facing resource page. Contains four module cards with slide deck downloads, specimen entry links, a downloadable lesson plan, and an instructor reference table with specimen identities. Explicitly not linked from student-facing pages (banner + footer both say so) — the splash page respects this by routing its primary click into student-landing.html, not here.

anthropology/student-landing.html — student-facing landing page with "phone call from someone who found bones" narrative framing, six locomotor type cards with IMI ranges, four YouTube video embeds showing locomotion types, four specimen cards linking to the investigation, and a separate, visually distinct "After You Finish The Investigation" section linking to assessment.html (kept apart from the specimen grid so it reads as a later summative step, not a 5th mystery specimen). That section is locked by default (greyed card, no link) and only unlocks into a clickable assessment.html link once a localStorage flag (epistemic_argument_feedback_received, set by investigation.html's submitArgument() on the first successful feedback response) is present. There's no backend or login, so this is client-side state per browser, not enforced completion — a student can clear storage or switch devices/browsers to bypass it — but it replaces what used to be an always-clickable link with only a text note asking students to finish first.

anthropology/investigation.html — the main investigation tool, single file with URL parameter switching (?specimen=MS11 through MS14). Contains five tabs: Limb Proportions, Body Mass, Olecranon Index, Bone Geometry, Build Argument. Loads 478-specimen limb length dataset and 111-specimen CSG dataset as embedded JSON. Runs Pyodide for scatter/box plots via Plotly. AI formative feedback on student arguments calls the Gemini API (gemini-3.5-flash, free tier) through a Cloudflare Worker proxy (cloudflare-worker/worker.js) so the API key never sits in this public page. Reveal (Tab 5) is gated behind a revised argument submission, not just the first one — see Tab 5 detail below.

anthropology/lesson-plan.pdf, anthropology/slides-*.pptx.pdf, anthropology/MomentMacro_CSATS.txt — instructor-facing downloads, all linked from instructor.html.

anthropology/assessment.html — end-of-unit assessment, linked from instructor.html (opens in a new tab, not a download). Generates a randomized transfer specimen client-side on load using a seeded PRNG (mulberry32); the seed lives in the URL so a reload keeps the same specimen but a fresh visit gets a new one. No two students (or sections, or semesters) get the same underlying numbers by default — this is the deliberate fix for the standard problem of assessment answers getting passed down. Randomization is template-based across three archetypes (suspensory_ceboid, cursorial_cercopithecoid, leaping_lemuroid), each with its own genuine multi-metric tension (mirroring the four mystery specimens' design), not naive independent-field randomization — that would risk generating a specimen that trivially resolves on one metric or is biologically implausible. Real embedded DATA and CSG_DATA (duplicated from investigation.html, not fetched) form the comparative backdrop in every chart; only the focal specimen's own numbers are generated. Five "data displays" (limb proportion scatter with a species/superfamily view toggle, IMI box plot, body mass table, an interactive click-to-mark OUI number line, CSG box plots with a CA/Imax-Imin toggle) plus ten questions across four parts: reading the displays (with an evidence-selection checklist per question — deliberately not every display is useful for every question), comparing to the student's own earlier mystery specimen, a full claim/evidence/conflicting-evidence/adaptation argument, and a reflection. Submission generates a printable summary (student responses + the exact specimen data they worked from) and a gated "reveal instructor grading reference" section that is auto-computed from that student's specific random values using the same classification logic as the rest of the platform (IMI category ranges, OUI_GROUPS from Drapeau 2004, the CSG interpretation heuristics), not written by hand per student. No backend or login; degrades gracefully if the Plotly CDN fails (each chart's render is independently wrapped, so one failure doesn't take down the body mass table, the OUI canvas, or the rest of the form). Operational note for instructors: the anti-sharing property only holds if students each open the assessment fresh — sharing the literal URL with a ?seed= already in it hands over the same specimen, so distribute the bare assessment.html link, not a URL a previous student generated.

logo.png at the repo root is the shared platform logo, referenced by both index.html and anthropology/instructor.html (via a relative ../logo.png path). Keep it at root rather than duplicating it per unit as more units are added.

The five investigation tabs in detail

Tab 1 (Limb Proportions): Configurable scatter plot and IMI box plot from 478 primate specimens across four superfamilies. Students enter four limb measurements (humerus, radius, femur, tibia), IMI calculates live, mystery specimen plots as a star. Grouping by superfamily/common name/genus. Axes fully configurable.

Tab 2 (Body Mass): Femoral head SI diameter input, five taxon-specific regression equations output simultaneously. Equations: Lemurs exp(2.548×ln(FHSI)+1.696)÷1000, South American Monkeys exp(2.729×ln(FHSI)+1.420)÷1000, Old World Monkeys exp(2.388×ln(FHSI)−4.560), Apes 10^(2.6465×log₁₀(FHSI)−2.4093), Humans 10^(1.7125×log₁₀(FHSI)−1.048). Contextual note auto-generates based on whether human estimate is biologically plausible.

Tab 3 (Olecranon Index): OL and UL inputs, OUI calculates live, plots as triangle on a canvas number line against six locomotor group ranges from Drapeau (2004). Groups staggered at three heights to prevent label overlap. Note explicitly states mid-range overlap means OUI alone cannot resolve classification.

Tab 4 (Bone Geometry): ImageJ link bar at top. Drag-and-drop upload for femur and humerus log files (tab-separated ImageJ MomentMacro output: Name, CA, Imax, Imin, Imax/Imin, J). Three switchable charts: log-scale J scatter with 1:1 reference line, Imax/Imin box plots, log-scale cortical area box plots. Femur/humerus/both toggle on box plots.

Tab 5 (Build Argument): Four structured prompts (claim, supporting evidence, conflicting evidence, adaptation/natural selection). Summary pills show all measurements student collected across tabs. Submission calls FEEDBACK_ENDPOINT (a Cloudflare Worker, see cloudflare-worker/worker.js) which holds the Gemini API key server-side and forwards to gemini-3.5-flash. Generates 240-290 word formative feedback that reads all four analyses, does not reveal identity, pushes back on single-metric arguments. The "Reveal identity" button and Identity Revealed panel live here (moved off Tab 1's sidebar so the unlock sits next to the action that earns it) and only arm after the student's second, revised argument submission gets feedback — the first submission's feedback alone does not unlock it, tracked via an in-page submission counter (argumentSubmitCount). A separate, smaller "assessment nudge" card also sits on this tab, always visible so it's discoverable even mid-demo: it starts in a greyed, locked state and flips to a live link to assessment.html once the first submission's feedback comes back, gated on the same epistemic_argument_feedback_received localStorage flag that unlocks the assessment section on student-landing.html. This was deliberately kept as a same-tab link rather than folded into investigation.html as a structural 6th tab, since the assessment generates an unrelated randomized specimen and is meant to be instructor-timed, not an automatic next step in the tab sequence.

The four mystery specimens

MS-11: Alouatta seniculus (Red Howler Monkey), Rio Verde Forest Reserve Colombia. IMI in arboreal quadruped range. Body mass 5-10kg distinguishes from larger species with similar IMI.

MS-12: Presbytis obscura (Dusky Leaf Monkey), Bukit Hijau National Park Malaysia. IMI ~90-91 in dense cercopithecoid overlap zone. Multiple locomotor strategies produce similar values.

MS-13: Indri indri, West African forest (deliberate misdirection — Indri is Malagasy). IMI ~66.5 clusters near humans and sifaka for entirely different evolutionary reasons. Two misdirections: field context wrong, IMI human-like but animal is a vertical clinger and leaper.

MS-14: Erythrocebus patas (Patas Monkey), Kiboko Savanna Sub-Saharan Africa. IMI overlaps with arboreal cercopithecoids despite highly terrestrial cursorial lifestyle. Fastest primate on ground ~55km/h. Habitat context is essential.

Datasets embedded in anthropology/investigation.html

Limb length: 478 specimens, four superfamilies (Hominoidea, Cercopithecoidea, Ceboidea, Lemuroidea), 21 common names. Fields: superfamily, genus, species, common_name, sex, humerus, radius, femur, tibia, forelimb, hindlimb, imi. Source: two Excel files (Limb_Length_Dataset_A and B) from Duke University collaborator.

CSG: 111 specimens, 11 species (Human, Chimp, Gorilla, Baboon, Orangutan, Siamang, Brown Capuchin, Sifaka, Squirrel Monkey, Howler Monkey, Crab-eating Macaque). Fields: common_name, femur_ca, humerus_ca, femur_j, humerus_j, femur_imax_imin, humerus_imax_imin. Log scale used throughout because size range spans two orders of magnitude.

Meteorology / Energy Balance unit (sandbox live and linked from the splash page; everything around it still a prototype)

Adapts a Colab notebook a high school physics teacher (Mr. Besong) has used for years — NASA CERES satellite energy-balance data, originally requiring an 800MB NetCDF file plus Cartopy/matplotlib for mapping, both incompatible with Pyodide — into a browser-only tool matching the platform's no-backend/no-external-dependency design. Lives under meteorology/ (promoted from meteorology/prototypes/ to match anthropology/'s flat top-level convention) and is linked from index.html's meteorology tile, badged "Prototype" rather than "Live" since it's only the bare sandbox tool — no narrative landing page, no instructor page, no guided investigations wrapping it yet, unlike anthropology's card.

meteorology/energy-balance-sandbox.html — single-file research sandbox. Students pick a display type (time series, scatter/correlation, or spatial trend map), a variable, a year range, a month selection (All/Winter DJF/Summer JJA quick-picks or custom), and a lat/lon region (Global/Arctic/Antarctic/Tropics/Hemisphere presets or a custom box), run the analysis, and log a "what do you see / what does it mean / what questions does it raise" notebook entry (localStorage key epistemic_energy_balance_notebook). No AI feedback or reveal mechanism yet, unlike the anthropology unit — this is still validating the underlying data/analysis machinery, not yet at the instructional-design layer.

Six raw variables (isr, rsr, olr, net, cld, clrolr — incoming solar, reflected shortwave, outgoing longwave, net flux, cloud fraction, clear-sky OLR) plus two derived (asr = isr−rsr, cre = olr−clrolr), matching real CERES EBAF-TOA product variables (solar_mon, toa_sw_all_mon, toa_lw_all_mon, toa_net_all_mon, cldarea_total_daynight_mon, toa_lw_clr_c_mon).

Two-tier resolution architecture: one always-loaded coarse dataset (2°, 90×180 grid, full globe, every month) for time series/scatter work and for scanning the whole globe on a trend map; separate fine-resolution (1°, native CERES resolution) tiles (30°×30° each, 72 tiles cover the globe) fetched only for whichever tiles a selected region overlaps, capped at 12 tiles (~17MB) before automatically falling back to the coarse dataset. This exists because a single global dataset at 1° was empirically ruled out (≈183MB, too large to load on every visit) and because trend maps at 2° were confirmed too coarse to read (a 30°×40° custom region is 300 cells at 2° vs 1200 at 1°).

Trend maps render via hand-rolled spherical projection math (equirectangular, orthographic, stereographic — Snyder's standard forward/inverse formulas), not Plotly's geo traces or Cartopy: Cartopy doesn't work in Pyodide (see above), and a scattergeo-marker approach was tried first and abandoned — no fixed marker size can correctly tile a lat/lon grid under a curved, non-cylindrical projection (confirmed by a visibly broken "pinwheel" render under stereographic at global extent). The working approach inverse-projects every output canvas pixel back to a lat/lon and looks up its cell, which is correct by construction for any projection. A bundled ~76KB world coastline file (110m resolution, decoded offline from the world-atlas npm package via topojson-client, not fetched live) draws over the raster for geographic orientation, clipped to the same region bounds as the data itself — an earlier version clipped coastlines only to the projection's own visibility, not the selected region, so coastlines from well outside the analyzed area could render past the edge of the data.

Data: real CERES EBAF-TOA Edition 4.2.1, monthly, 2001-2025 (25 full years — the record starts March 2000 and the available subset ends April 2026, so both partial-coverage years were dropped). Quantized to int16 with a single global scale factor, gzip-compressed. Getting this data in is worth remembering for next time: this sandbox has no route to fetch anything from NASA Earthdata or Google Drive, so the conversion has to run in a Python environment that already has the file (Colab, in this case), sending back only the small processed output — and even that small output had real trouble getting from a local computer into GitHub. The ~39.5MB coarse file was too large for GitHub's web upload flow; a subsequent attempt got mangled into garbled text after the .gz extension triggered the OS's own archive handler to silently decompress it, and the resulting garbage got pasted through GitHub's "create new file" text editor instead of uploaded as binary. What finally worked: strip the .gz extension entirely before the file leaves Colab (a plain unlabeled binary blob nothing tries to "helpfully" touch), then push via GitHub Desktop rather than the website upload widget, which also silently drops files into the wrong folder when uploaded in separate batches. Verified end to end afterward: decompressed byte counts match the manifest exactly, and the tool's own area-weighted global mean for incoming solar radiation comes out to 340.5 W/m², matching the well-known published value.

Important distinction: the Colab notebook referenced above (Mr. Besong's original lesson, used as the source for the sandbox's data/analysis logic) predates public generative AI availability and contains no AI/API calls of any kind — there is no exposed key in it and nothing to route through the Cloudflare Worker. This was previously misdocumented in this file; if AI feedback ever gets asked about for the meteorology unit, it means a new feature to design, not a fix to something already in that notebook.

Terminology note: when this unit's design talks about a "notebook," across every mention in this file it means a pedagogical science notebook — a student-facing log of what was studied, why, what was found, and what it led to (claim/evidence/reasoning), the same spirit as Tab 5's argument-building in the anthropology unit. It does not mean a Jupyter-style code notebook, and Pyodide is not involved in it.

Planned but not started: an instructor resource page and a sequence of guided investigations (mirroring anthropology/instructor.html and the investigation tabs) are designed at the outline level — walking students through energy balance concepts using the existing sandbox (incoming vs. reflected solar, outgoing longwave and the greenhouse effect via clear-sky OLR, clouds' dual cooling/warming role, trends and regional patterns like polar amplification), each step feeding a science-notebook entry — but building is on hold pending feedback from Max before proceeding. Further out, after guided investigations, students would move to a novel open-ended research project using the same sandbox, with AI feedback on their analyses; this is explicitly harder than the anthropology unit's Tab 5 pattern because there's no fixed specimen set or answer key to check an open-ended research claim against, so it needs real design work (tightly scoped prompting to limit hallucination/bad feedback) before it gets built, not just a copy of the existing Cloudflare Worker route.

What is deliberately deferred

Instructor view/dashboard: deferred to v1.5. CSV export is interim solution. LMS integration (LTI 1.3) deferred to v1.5. A lesson plan with learning objectives now exists (anthropology/lesson-plan.pdf), written for an intro undergraduate biological anthropology course and framed against AAAS Vision and Change core competencies rather than NGSS (NGSS is K-12 only and doesn't fit that audience). If a K-12 version of this or another unit is built later, it would need its own NGSS-aligned pass. Accounts/login: deferred, but the splash page now has a placeholder for it. This is a real, intended feature, not something Matt has decided against — individual student logins, a teacher-side view, and grade passback into Canvas/Brightspace/Google Classroom are all wanted eventually. LTI 1.3 is the standard mechanism that covers all three LMSs with one integration rather than three separate ones. But per the "Current stage" note at the top of this file, none of that gets built during this proof-of-concept phase — it's explicitly earmarked for the future hired software engineer, not for Claude/Matt to build now. Do not start scaffolding auth, a database, or a backend for this reason; keep new units static and no-login like anthropology and meteorology currently are. Meteorology unit: the core research sandbox is built, running on real CERES data (including region-scoped trend maps with proper geographic projections, see the dedicated section above), promoted to meteorology/ and linked live from the splash page as a standalone "Prototype" tile — but an instructor resource page, guided investigations, an end-of-unit assessment, a poster template (optional end deliverable, explicitly not pulling from logged notebook entries), and an AI feedback/reveal loop are all still deferred — see "Planned but not started" in the meteorology section above for the current design thinking on the first two of those.

Fine-resolution tiles are global at a fixed 30°×30° granularity generated from the real CERES data; if finer tiles or a different tiling scheme are wanted later, regenerate via the same manifest+gzip pattern (documented in the meteorology section above), not by hand. GitHub's web upload UI has repeatedly proven unreliable for this project's larger binary assets (mis-files them into the wrong folder when uploaded in separate batches, silently drops files over roughly 25MB, and its "create new file" text editor will silently corrupt binary content if it's ever used by mistake instead of the file-upload flow) — GitHub Desktop is the reliable path for anything of meaningful size going forward.
